# ECHO — 문제 정의 (2026-09-01, 실측 기반 확정판)

## 확정된 사실 (실측/코드로 검증됨)

1. **ZERO의 particle_filter**는 라이다 스캔이 들어올 때마다(40Hz, 25ms 예산) `MCL()`을
   실행 — 리샘플(이전 사이클 가중치 사용) → 센서모델(레이마칭+평가) → 정규화, 순서로 동작.
   (`particle_filter.py:753-806`, `lidarCB→update→MCL` 호출 체인 코드로 확인)
2. **레이마칭이 압도적 비중** — 센서모델 함수 안에서 90%+ (500파티클 89.6%, 4000파티클
   90~95%). 참고문헌(Bernardi et al., DATE 2022, 같은 알고리즘)도 동일하게 90%. **3중 확인.**
3. **이 개발 PC(WSL)에서는 PF가 병목이었던 적이 없음** — `fine_timing:1`로 실측:
   - 500파티클: possible ≈ 620Hz (요구 40Hz 대비 15배 여유)
   - 4000파티클: possible ≈ 88Hz (요구 40Hz 대비 2.2배 여유) — **목표치인 4000개도 이 PC
     에선 여유롭게 40Hz를 맞춤**
   - 두 경우 다 실제 달성 속도(`iters per sec`)는 안정적으로 ~40Hz
4. **`max_particles: 500` 임시 하향(2026-08-07, 한 달 가까이 미복원)의 진짜 원인은
   PF 자체가 아니라 `opponent_perception`(당시 동시 실행, O(n²) 버그로 7초+까지 걸렸던
   노드)일 가능성이 높음** — 위 3번 실측이 그 가설을 뒷받침(PF 단독으론 무죄).

## 확정 못한 것 (알려진 갭)

- **실차 Jetson에서의 실측 없음.** 위 숫자는 전부 개발 PC(WSL) 기준 — Jetson은 훨씬
  약한 CPU라, 여기서 본 여유(2.2배~15배)가 Jetson에서도 그대로 유지될지는 미지수.
- `opponent_perception`과 동시에 돌 때 PF가 실제로 얼마나 밀리는지도 미실측.

## 목표 (재정의)

**A. 학습/포트폴리오 목표** (불변)
- Verilog RTL → Icarus 시뮬레이션 → (보드 확정 시) 합성/타이밍까지 완주
- 삼성DS 회로설계 직무 포트폴리오 수준

**B. 기술 목표 (정직하게 재구성)**
- ~~"PF가 25ms를 못 맞춘다"~~ — 개발 PC에서 반증됨, 이 주장 폐기
- 대신: **"particle filter의 반복연산(특히 레이마칭)이 CPU 예산의 대부분을 차지하는
  구조는 실측으로 확정됐고, 이게 임베디드급(Jetson) 환경이나 다른 무거운 노드와 동시
  실행 시 실제 병목이 될 위험이 있다"**는 것을 근거로, 그 연산을 병렬 하드웨어로
  가속하는 RTL을 설계·검증한다. Jetson 실측이 없다는 한계는 정직하게 명시.
- 기존 문헌(Bernardi 2022: 산업용 대형 Zynq + HLS 자동합성)과의 차별화는 여전히 유효:
  수작업 RTL, 소형 교육용 보드.

**C. 타깃 순서 — 확정 (2026-09-01)**
레이마칭이 압도적 손잡이라는 게 데이터로 확인됐지만, **v1은 센서모델평가로 확정.**
이유: 이미 설계(Q5.8 로그테이블+룩업+덧셈 PE)가 끝나있고, 첫 RTL 프로젝트로 난이도가
적당하며, 논문이 안 건드린 gap이라는 차별점도 유효. **레이마칭은 v2로 이어감** —
센서모델 PE로 RTL/시뮬레이션/GTKWave 워크플로우를 완주한 뒤 착수.
