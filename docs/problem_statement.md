# ECHO — 문제 정의 (2026-09-01, 실측 기반 확정판)

## 확정된 사실 (실측/코드로 검증됨)

1. **ZERO의 particle_filter**는 라이다 스캔이 들어올 때마다(40Hz, 25ms 예산) `MCL()`을
   실행 — 리샘플(이전 사이클 가중치 사용) → 센서모델(레이마칭+평가) → 정규화, 순서로 동작.
   (`particle_filter.py:753-806`, `lidarCB→update→MCL` 호출 체인 코드로 확인)
2. **레이마칭이 압도적 비중** — 센서모델 함수 안에서 90%+ (500파티클 89.6%, 4000파티클
   90~95%). 참고문헌(Bernardi et al., DATE 2022, 같은 알고리즘)도 동일하게 90%. **3중 확인.**
3. **이 개발 PC(WSL)에서는 PF가 병목이었던 적이 없음** — `fine_timing:1`로 실측:
   - 500파티클: possible ≈ 620Hz (요구 40Hz 대비 15배 여유)
   - 4000파티클: possible ≈ 88Hz (요구 40Hz 대비 2.2배 여유) — **목표치인 4000개도 이 PC
     에선 여유롭게 40Hz를 맞춤**
   - 두 경우 다 실제 달성 속도(`iters per sec`)는 안정적으로 ~40Hz
4. **`max_particles: 500` 임시 하향(2026-08-07, 한 달 가까이 미복원)의 진짜 원인은
   PF 자체가 아니라 `opponent_perception`(당시 동시 실행, O(n²) 버그로 7초+까지 걸렸던
   노드)일 가능성이 높음** — 위 3번 실측이 그 가설을 뒷받침(PF 단독으론 무죄).

## 확정 못한 것 (알려진 갭)

- **실차 Jetson에서의 실측 없음.** 위 숫자는 전부 개발 PC(WSL) 기준 — Jetson은 훨씬
  약한 CPU라, 여기서 본 여유(2.2배~15배)가 Jetson에서도 그대로 유지될지는 미지수.
- `opponent_perception`과 동시에 돌 때 PF가 실제로 얼마나 밀리는지도 미실측.

### 2026-09-02 추가 — "FPGA가 실제 ZERO보다 빠르다"는 아직 증명 안 됨

v1~v3 + 합성 + arbiter 기반 BRAM 공유(1→8파티클)까지 실측으로 확정했지만,
**이게 실제 ZERO의 particle_filter를 대체했을 때 진짜 더 빠른지는 완전히
별개의, 아직 열린 질문**이다. 구체적 격차:

- **빔 개수**: v3(`particle_scorer` 계열, pair/quad/oct_arb 전부)는 `NUM_RAYS=8`
  로만 검증됨. 실제 ZERO는 빔 60개 — v1(`sensor_pe` 단독)만 60빔으로 검증됐고,
  레이마칭까지 합친 전체 파이프라인은 60빔으로 한 번도 안 돌려봄.
- **입력 형태 불일치**: `particle_scorer`는 빔마다 `dx, dy`(방향벡터)를 직접
  포트로 받음. 실제 ZERO(`range_libc`)는 파티클 `(x, y, θ)` + 스캔만 받아서
  내부적으로 파티클 헤딩과 라이다 각도 오프셋을 합쳐 방향을 계산함 — 그대로
  붙이면 Jetson이 파티클마다 60개 방향벡터(cos/sin)를 미리 계산해서 스트리밍
  해줘야 함. **이 삼각함수 계산 비용 자체를 한 번도 측정 안 함** — range_libc가
  지금 pose→ray 변환을 최적화된 C++로 한 번에 처리하는데, FPGA로 떼어간 게
  테이블 룩업뿐이라면 삼각함수 계산이 원가의 상당 부분을 차지했을 경우 실제
  절감폭이 기대보다 작을 수 있음.
- **파티클 규모**: 지금까지 검증한 건 최대 8파티클(합성 실측 기준). ZERO의
  현재 운용치는 500, 원래 설계 목표는 4000 — 이 격차를 메꾸는 스트리밍
  아키텍처(500~4000개를 순차/파이프라인으로 처리)는 미착수.
- **엔드투엔드 실측 없음**: 지금 있는 건 RTL 시뮬레이션 클럭 수와 (post-synth,
  이제 post-route 예정) 합성 타이밍뿐. "스캔 도착 → weight 확정"까지의 실제
  경과시간, Jetson↔FPGA 통신 구조·오버헤드는 전부 미정.
- **정확도 비교 없음**: RTL은 파이썬 고정소수점 오라클과는 비트 단위로 일치
  검증했지만, 그 오라클 자체가 ZERO의 실제 float64 `range_libc` 계산과 완전히
  같은 결과를 내는지는 미확인 — 양자화 오차가 실제 위치추정 정확도(weight
  순위, ESS, 최종 localization 오차)에 영향을 주는지 아직 안 봄.

**결론(정직하게)**: ECHO는 지금 "FPGA 가속 가능성을 보이는 sensor-model
core"이며, 실제 particle filter의 end-to-end speedup은 아직 미검증이다.

**다음 우선순위는 성능 최적화보다 동일 조건 벤치마크**:
1. ZERO에서 실제 스캔 60개·파티클 500개를 한 프레임 덤프
2. `range_libc`의 ray casting / sensor evaluation / 전체 sensor_model 시간을
   각각(그리고 방향벡터 삼각함수 계산 비용도 별도로) 측정
3. ECHO를 60빔·500파티클 스트리밍 입력까지 확장하고 총 클럭 측정
4. 두 결과의 weight 순위·ESS·최종 localization 오차 비교
5. Jetson↔FPGA 통신 시간까지 더해 비교

가설(미검증): 500파티클에서는 `range_libc`가 이미 충분히 빨라서 외부 FPGA
통신 오버헤드가 이득을 상쇄할 수 있고, 4000파티클 이상에서 ECHO의 병렬화
이점이 더 설득력 있어질 가능성이 큼 — 벤치마크 전까지는 가설일 뿐.

### 2026-09-02 추가2 — 위 5단계 중 2·3번 첫 실측/추정치 확보 (4·5번은 여전히 미착수)

**2번(range_libc 컴포넌트별 시간)**: 실제 ZERO 코드(`particle_filter.py`)에
이미 있던 `fine_timing` 진단 훅을 켜서 표준 스모크 테스트(`sim:=true
planner:=none controller:=pure_pursuit`, changwon 트랙)로 145개 샘플 실측(WSL
CPU, **Jetson 실측 아님** — 아래 캐비엇 참고). `range_method="rm"`(레이마칭,
ECHO와 같은 알고리즘 계열), `rangelib_variant=2`, `num_rays=60`,
`max_particles=500`(둘 다 ECHO가 맞추려는 실제 목표치와 정확히 일치):
| 구간 | 평균(ms) |
|---|---|
| ray casting(`calc_range_repeat_angles`) | 1.294 |
| sensor eval(`eval_sensor_model`) | 0.082 |
| sensor_model() 전체(init+range+eval+squash) | 1.428 |

**3번(ECHO를 60빔으로 확장)**: RTL은 빔 개수에 파라미터화 안 돼있고 "빔
시작을 몇 번 주느냐"로만 정해지므로 재합성 없이 테스트벤치만 60빔으로
확장(`tools/gen_particle_scorer_60beam_test.py`). 실측(시뮬레이션 사이클,
oct_arb의 post-synth WNS -2.438ns → 달성 가능 클럭 ≈80.4MHz로 환산):
| 구성 | 사이클 | 시간(80.4MHz 기준) |
|---|---|---|
| 파티클 1개, 60빔 | 959 | 11.93μs |
| 파티클 8개 동시(arbiter8), 60빔 | 1300 | 16.17μs |

**500파티클 추정(측정 아님 — 8개씩 63배치를 순차로 돌린다고 가정한 계산)**:
63 × 16.17μs ≈ **1.02ms**. 실제 스트리밍 구현이면 배치 간 파이프라이닝으로
더 빨라질 수 있지만(다음 배치의 레이마칭과 이번 배치의 테이블 접근이
안 겹치므로) 그건 미설계 — 이 값은 보수적(비관적) 추정.

**비교(참고용, 아직 "증명"은 아님)**: ECHO 추정 1.02ms vs ZERO 실측 1.43ms
→ 이 조건에서 ECHO가 약 1.4배 빠를 수 있음. **단, 8-way 병렬화 없이 파티클을
하나씩 순차로 돌리면(959사이클×500 = 47.95만 사이클 ≈ 5.97ms) 오히려
ZERO 소프트웨어(1.43ms)보다 4배 이상 느림** — arbiter 기반 병렬화가 "이득이
아니라 필수조건"이라는 걸 이번에 처음으로 숫자로 확인.

**아직도 안 된 것(중요도 순)**:
1. **Jetson 실측 아님** — 위 1.428ms는 이 노트북(WSL) CPU 실측치. Jetson은
   이 노트북보다 훨씬 느릴 가능성이 높아 실제 배포 환경 비교는 더 유리하게
   나올 수 있지만, 이건 기대일 뿐 측정 안 함.
2. **500파티클 ECHO 값은 추정이지 시뮬레이션 실측이 아님** — 8파티클 배치를
   실측하고 63배 곱한 것. 실제 500파티클(또는 4000파티클) 풀 스트리밍
   테스트벤치는 아직 안 만듦.
3. **삼각함수(cos/sin) 계산 비용 여전히 미측정** — `particle_scorer`가 빔마다
   `dx,dy`를 직접 받는 구조라, Jetson이 파티클×60빔마다 이 방향벡터를
   미리 계산해줘야 하는 비용이 위 range_libc 실측에는 안 잡혀있음(range_libc
   내부는 pose+각도를 그대로 받아 자체 좌표변환하지, dx/dy를 요구 안 함 —
   ECHO 인터페이스가 그만큼 더 많은 전처리를 Jetson에 떠넘기는 구조).
4. **통신 비용(Jetson↔FPGA) 여전히 완전 미정** — 5번 그대로 미착수.
5. **정확도 비교 여전히 안 함** — 4번 그대로 미착수.

**결론(정직하게, 갱신)**: 순수 계산 사이클만 놓고 보면 ECHO가 이길 가능성을
처음으로 숫자로 보여줬지만(8-way 병렬화 있을 때만), 이건 "Jetson이 아닌
노트북과, 통신비용 0원인 FPGA를 비교한 낙관적 상한"에 가깝다 — 위 3,4번이
빠지면 실제 이득은 이보다 작아질 것이 거의 확실.

### 2026-09-02 추가3 — 위 3번(삼각함수 비용) 실측 결과: 현재 인터페이스로는 이득이 사라짐

바로 위 "3. 삼각함수 계산 비용 여전히 미측정"을 실제로 재고, **결론이
뒤집혔다.** 실제 ZERO 프레임(파티클 500개, 실제 스캔, `range_libc` 예측거리·
weight)을 `bench/zero_frame_001.npz`로 처음 확보(`fine_timing` 훅에 이어
새 `ECHO_FRAME_DUMP` 훅 추가, 측정 후 원복 — 이번엔 되돌리기 전 diff 확인해
사고 재발 없었음)하고, 이 500개 실제 파티클을 그대로 ECHO 파이프라인에
흘려 세 가지를 동시에 실측:

1. **500파티클 진짜 스트리밍 실측(추정 아님)**: 8개씩 63배치로 실제 RTL을
   순차 실행 — **72,289 사이클**(8-way post-synth 클럭 기준 ≈0.899ms). 지난
   추정(63×1300=81,900사이클)보다 11.7% 적어 오히려 낙관적이었음이 확인됨.
2. **Jetson dx,dy 전처리 비용**: 500×60=30000쌍 방향벡터를 벡터화 numpy로
   생성 — **0.782ms/frame**(이 노트북 CPU, 벡터화 기준 — 실제 Jetson 구현도
   이렇게 할 것이므로 공정한 하한).
3. **정확도(weight 순위/ESS)**: ECHO가 500개 파티클의 **실제 theta까지 반영**해
   재계산(`gen_real_frame_test.py`) — Spearman 순위상관 0.998로 전체적으론
   거의 일치하지만, **상위 10개 겹침 1/10**, **ESS 23.4%(ECHO) vs 63.5%(ZERO
   실측)**로 정확도 격차가 실측으로 처음 확인됨(원인 미규명).

**종합**: FPGA 연산 자체(0.899ms)는 여전히 ZERO(1.428ms)보다 빠르지만,
**"Jetson이 dx,dy를 미리 계산해서 준다"는 현재 `particle_scorer` 인터페이스를
포함하면 0.899+0.782=1.681ms로 오히려 18% 더 느려진다.** 통신비용(여전히
미측정)까지 더하면 격차는 더 벌어질 것. **위 3번 항목에서 예상했던 우려("삼각함수
계산 비용이 원가의 상당 부분을 차지해 절감폭이 기대보다 작을 수 있다")가
실측으로 확정됐고, 실제로는 "작아지는" 정도가 아니라 "역전"됨.**

**결론(정직하게, 재갱신)**: 지금 인터페이스(빔마다 `dx,dy` 외부 입력)로는
ECHO가 실제 ZERO보다 빠르다고 주장할 수 없다 — 오히려 느리다. FPGA가
`(x,y,θ)`+`beam_id`를 직접 받아 내부에서 방향벡터를 생성하는 구조(direction
generator 내장)가 사실상 필수 조건으로 보인다 — 다음 세션 최우선 설계 과제.
정확도 격차(ESS 23.4% vs 63.5%)도 원인 미규명 상태로 남아있어, 속도 문제가
풀려도 정확도 문제가 별도로 남아있음.

**8-way(oct_arb) post-route로 위 수치 확정(post-synth 추정 대체)**: WNS
-2.438ns(추정) → **-2.653ns(실측, ≈79.0MHz)**, BRAM/DSP 동일(39/50, 0),
크리티컬 패스도 동일(`ray_march_edt`의 EDT 배럴시프터). 이 클럭으로
재계산하면 FPGA 연산 500파티클 0.915ms(+Jetson 전처리 포함 1.697ms) — 위
결론(현재 인터페이스로는 18~19% 느림, direction generator 필요)은 그대로
유지됨, post-route가 결론을 안 뒤집었다는 뜻.

**⚠️ 위 8-way 수치의 캐비엇 — `HD.CLK_SRC` 미설정**: GUI에서 같은 tcl을 독립
재실행해 WNS -2.659ns(배치 -2.653ns와 거의 일치, 재현성 확인)를 얻었으나,
이번엔 `WARNING: [Timing 38-242] HD.CLK_SRC of clock port "clk" is not set.
In out-of-context mode, this prevents timing estimation for clock
delay/skew`를 확인함. oct_arb를 IO 핀 부족(850포트 vs 210핀) 때문에
`-mode out_of_context`로 돌린 대가로, **클럭이 실제 어디서 들어오는지
모르는 상태라 클럭 네트워크의 delay/skew 추정이 불완전**함 — 즉 8-way의
post-route 수치는 "내부 로직 경로는 진짜 실측, 클럭 모델은 불완전한 추정"
이라는 조건이 붙어있었음(1파티클 `particle_scorer`는 진짜 top이라 해당
없음). 완전히 없애려면 실제 top-level 랩퍼 안에 넣거나 `HD.CLK_SRC`를
수동 지정해야 함 — 다음 세션 검토 대상.

**B. 기술 목표 (정직하게 재구성)**
- ~~"PF가 25ms를 못 맞춘다"~~ — 개발 PC에서 반증됨, 이 주장 폐기
- 대신: **"particle filter의 반복연산(특히 레이마칭)이 CPU 예산의 대부분을 차지하는
  구조는 실측으로 확정됐고, 이게 임베디드급(Jetson) 환경이나 다른 무거운 노드와 동시
  실행 시 실제 병목이 될 위험이 있다"**는 것을 근거로, 그 연산을 병렬 하드웨어로
  가속하는 RTL을 설계·검증한다. Jetson 실측이 없다는 한계는 정직하게 명시.
- 기존 문헌(Bernardi 2022: 산업용 대형 Zynq + HLS 자동합성)과의 차별화는 여전히 유효:
  수작업 RTL, 소형 교육용 보드.

**C. 타깃 순서 — 확정 (2026-09-01)**
레이마칭이 압도적 손잡이라는 게 데이터로 확인됐지만, **v1은 센서모델평가로 확정.**
이유: 이미 설계(Q5.8 로그테이블+룩업+덧셈 PE)가 끝나있고, 첫 RTL 프로젝트로 난이도가
적당하며, 논문이 안 건드린 gap이라는 차별점도 유효. **레이마칭은 v2로 이어감** —
센서모델 PE로 RTL/시뮬레이션/GTKWave 워크플로우를 완주한 뒤 착수.
