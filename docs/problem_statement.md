# ECHO — 문제 정의 (2026-09-01, 실측 기반 확정판)

## 확정된 사실 (실측/코드로 검증됨)

1. **ZERO의 particle_filter**는 라이다 스캔이 들어올 때마다(40Hz, 25ms 예산) `MCL()`을
   실행 — 리샘플(이전 사이클 가중치 사용) → 센서모델(레이마칭+평가) → 정규화, 순서로 동작.
   (`particle_filter.py:753-806`, `lidarCB→update→MCL` 호출 체인 코드로 확인)
2. **레이마칭이 압도적 비중** — 센서모델 함수 안에서 90%+ (500파티클 89.6%, 4000파티클
   90~95%). 참고문헌(Bernardi et al., DATE 2022, 같은 알고리즘)도 동일하게 90%. **3중 확인.**
3. **이 개발 PC(WSL)에서는 PF가 병목이었던 적이 없음** — `fine_timing:1`로 실측:
   - 500파티클: possible ≈ 620Hz (요구 40Hz 대비 15배 여유)
   - 4000파티클: possible ≈ 88Hz (요구 40Hz 대비 2.2배 여유) — **목표치인 4000개도 이 PC
     에선 여유롭게 40Hz를 맞춤**
   - 두 경우 다 실제 달성 속도(`iters per sec`)는 안정적으로 ~40Hz
4. **`max_particles: 500` 임시 하향(2026-08-07, 한 달 가까이 미복원)의 진짜 원인은
   PF 자체가 아니라 `opponent_perception`(당시 동시 실행, O(n²) 버그로 7초+까지 걸렸던
   노드)일 가능성이 높음** — 위 3번 실측이 그 가설을 뒷받침(PF 단독으론 무죄).

## 확정 못한 것 (알려진 갭)

- **실차 Jetson에서의 실측 없음.** 위 숫자는 전부 개발 PC(WSL) 기준 — Jetson은 훨씬
  약한 CPU라, 여기서 본 여유(2.2배~15배)가 Jetson에서도 그대로 유지될지는 미지수.
- `opponent_perception`과 동시에 돌 때 PF가 실제로 얼마나 밀리는지도 미실측.

### 2026-09-02 추가 — "FPGA가 실제 ZERO보다 빠르다"는 아직 증명 안 됨

v1~v3 + 합성 + arbiter 기반 BRAM 공유(1→8파티클)까지 실측으로 확정했지만,
**이게 실제 ZERO의 particle_filter를 대체했을 때 진짜 더 빠른지는 완전히
별개의, 아직 열린 질문**이다. 구체적 격차:

- **빔 개수**: v3(`particle_scorer` 계열, pair/quad/oct_arb 전부)는 `NUM_RAYS=8`
  로만 검증됨. 실제 ZERO는 빔 60개 — v1(`sensor_pe` 단독)만 60빔으로 검증됐고,
  레이마칭까지 합친 전체 파이프라인은 60빔으로 한 번도 안 돌려봄.
- **입력 형태 불일치**: `particle_scorer`는 빔마다 `dx, dy`(방향벡터)를 직접
  포트로 받음. 실제 ZERO(`range_libc`)는 파티클 `(x, y, θ)` + 스캔만 받아서
  내부적으로 파티클 헤딩과 라이다 각도 오프셋을 합쳐 방향을 계산함 — 그대로
  붙이면 Jetson이 파티클마다 60개 방향벡터(cos/sin)를 미리 계산해서 스트리밍
  해줘야 함. **이 삼각함수 계산 비용 자체를 한 번도 측정 안 함** — range_libc가
  지금 pose→ray 변환을 최적화된 C++로 한 번에 처리하는데, FPGA로 떼어간 게
  테이블 룩업뿐이라면 삼각함수 계산이 원가의 상당 부분을 차지했을 경우 실제
  절감폭이 기대보다 작을 수 있음.
- **파티클 규모**: 지금까지 검증한 건 최대 8파티클(합성 실측 기준). ZERO의
  현재 운용치는 500, 원래 설계 목표는 4000 — 이 격차를 메꾸는 스트리밍
  아키텍처(500~4000개를 순차/파이프라인으로 처리)는 미착수.
- **엔드투엔드 실측 없음**: 지금 있는 건 RTL 시뮬레이션 클럭 수와 (post-synth,
  이제 post-route 예정) 합성 타이밍뿐. "스캔 도착 → weight 확정"까지의 실제
  경과시간, Jetson↔FPGA 통신 구조·오버헤드는 전부 미정.
- **정확도 비교 없음**: RTL은 파이썬 고정소수점 오라클과는 비트 단위로 일치
  검증했지만, 그 오라클 자체가 ZERO의 실제 float64 `range_libc` 계산과 완전히
  같은 결과를 내는지는 미확인 — 양자화 오차가 실제 위치추정 정확도(weight
  순위, ESS, 최종 localization 오차)에 영향을 주는지 아직 안 봄.

**결론(정직하게)**: ECHO는 지금 "FPGA 가속 가능성을 보이는 sensor-model
core"이며, 실제 particle filter의 end-to-end speedup은 아직 미검증이다.

**다음 우선순위는 성능 최적화보다 동일 조건 벤치마크**:
1. ZERO에서 실제 스캔 60개·파티클 500개를 한 프레임 덤프
2. `range_libc`의 ray casting / sensor evaluation / 전체 sensor_model 시간을
   각각(그리고 방향벡터 삼각함수 계산 비용도 별도로) 측정
3. ECHO를 60빔·500파티클 스트리밍 입력까지 확장하고 총 클럭 측정
4. 두 결과의 weight 순위·ESS·최종 localization 오차 비교
5. Jetson↔FPGA 통신 시간까지 더해 비교

가설(미검증): 500파티클에서는 `range_libc`가 이미 충분히 빨라서 외부 FPGA
통신 오버헤드가 이득을 상쇄할 수 있고, 4000파티클 이상에서 ECHO의 병렬화
이점이 더 설득력 있어질 가능성이 큼 — 벤치마크 전까지는 가설일 뿐.

## 목표 (재정의)

**A. 학습/포트폴리오 목표** (불변)
- Verilog RTL → Icarus 시뮬레이션 → (보드 확정 시) 합성/타이밍까지 완주
- 삼성DS 회로설계 직무 포트폴리오 수준

**B. 기술 목표 (정직하게 재구성)**
- ~~"PF가 25ms를 못 맞춘다"~~ — 개발 PC에서 반증됨, 이 주장 폐기
- 대신: **"particle filter의 반복연산(특히 레이마칭)이 CPU 예산의 대부분을 차지하는
  구조는 실측으로 확정됐고, 이게 임베디드급(Jetson) 환경이나 다른 무거운 노드와 동시
  실행 시 실제 병목이 될 위험이 있다"**는 것을 근거로, 그 연산을 병렬 하드웨어로
  가속하는 RTL을 설계·검증한다. Jetson 실측이 없다는 한계는 정직하게 명시.
- 기존 문헌(Bernardi 2022: 산업용 대형 Zynq + HLS 자동합성)과의 차별화는 여전히 유효:
  수작업 RTL, 소형 교육용 보드.

**C. 타깃 순서 — 확정 (2026-09-01)**
레이마칭이 압도적 손잡이라는 게 데이터로 확인됐지만, **v1은 센서모델평가로 확정.**
이유: 이미 설계(Q5.8 로그테이블+룩업+덧셈 PE)가 끝나있고, 첫 RTL 프로젝트로 난이도가
적당하며, 논문이 안 건드린 gap이라는 차별점도 유효. **레이마칭은 v2로 이어감** —
센서모델 PE로 RTL/시뮬레이션/GTKWave 워크플로우를 완주한 뒤 착수.
